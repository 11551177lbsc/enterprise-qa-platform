# 企业支持解决中心：产品与工程路线

## 1. 产品定位

本项目定位为“企业知识支持与工单闭环 Agent”，不做没有业务边界的通用聊天机器人。

它面向两个典型角色：

- 员工或客户：希望快速得到有出处、可执行的解决办法；解决不了时不想重复描述问题。
- 支持人员或知识管理员：希望减少重复问答、收到信息完整的工单，并知道知识库缺少什么。

核心价值链是：

```text
描述问题
  → 检索受控知识
  → 返回答案、证据和置信度
  → 证据不足时生成工单草稿
  → 用户确认
  → 写入工单系统并可持续跟踪
  → 未解决问题反哺知识库建设
```

## 2. 当前基线与主要缺口

### 已有能力

- Java 用户认证、JWT、BCrypt、Redis 登录状态。
- LangGraph 显式状态机、Redis checkpoint、运行状态和事件。
- ChromaDB 知识检索和来源引用。
- 用户资料和工单的读写工具。
- 写操作人工审批、双重鉴权、幂等键、乐观锁、审计记录和 Outbox。
- Python 与 Java 自动化测试。

### 需要解决的产品问题

- 原页面要求手工填写 Agent API、复制 JWT，只适合开发调试。
- 原知识回答只是展示检索片段，没有明确“已解决还是应升级”。
- 检索证据弱时仍缺少标准化的人工接管入口。
- 工单只有标题、描述、优先级和状态，缺少分类、SLA、负责人和处理轨迹。
- 知识库缺少租户、权限、版本、审核、失效时间和反馈闭环。
- 评测主要覆盖工具路由，还没有完整的检索质量、忠实度和业务成功率基线。

## 3. 产品原则

1. **证据优先**：答案必须能回到具体知识片段；证据不足时明确拒绝猜测。
2. **写入可控**：模型只能提出工单或通知方案，最终写入必须由用户确认。
3. **身份不由模型决定**：用户身份只来自 JWT，Java 业务层再次校验资源归属。
4. **失败可恢复**：长任务有运行状态、checkpoint、幂等键和可重试边界。
5. **指标不造假**：所有效果数字都由版本化评测集或真实运行数据产生。
6. **先做闭环再扩功能**：每个阶段都必须能从用户入口走到可验收结果。

## 4. 分阶段实施

截至 2026-09-02，P0 已完成；P1 的分类、SLA、时间线、反馈和知识缺口闭环已进入代码；P2 已完成知识缺口治理与角色边界，文档级 ACL/版本管理仍需真实租户模型后实施；P3 已完成第一批并发终态保护、失败审计和检索评测；P4 已提供隔离网络、Nginx 网关和完整容器编排模板，但尚未在生产基础设施部署。

### P0：可用的支持闭环（当前阶段）

目标：让项目从“技术演示”变成可以实际走通的支持工作台。

- 页面内注册、登录和退出，不再让用户复制 JWT。
- 服务地址改由环境变量管理，不暴露为普通表单项。
- 知识结果增加 `outcome`、`confidence`、`reason`、`nextSteps`。
- 最佳知识匹配度低于安全阈值时，不直接回答，生成结构化工单草稿。
- 工单草稿按安全风险和不可用程度推断优先级。
- 用户点击升级后进入已有 Human-in-the-loop 审批，批准前零副作用。
- 增加高置信回答、低置信升级和结构化工单字段测试。

验收场景：

1. “扫地机器人无法回充怎么办”返回知识答案、来源和置信度。
2. 与知识库无关的问题返回低置信提示和工单草稿，不生成虚构答案。
3. 点击升级后先显示将写入的字段；拒绝时数据库无新增，批准时只新增一张工单。
4. 重复工具调用不会重复创建工单。

### P1：支持团队真正可管理

目标：从“用户自助 + 建单”扩展到可分派、可追踪的支持流程。

- 工单增加 `category`、`productModel`、`assignee`、`slaDueAt`、`resolutionCode`。
- 新增工单时间线，记录状态变化、补充信息、审批和通知事件。
- 增加支持人员角色和 RBAC，区分用户、坐席、知识管理员。
- 根据关键词、产品型号和严重程度做确定性 SLA 分流，模型只提供建议。
- 支持用户对答案执行“已解决 / 未解决”反馈；未解决反馈可一键带入工单。
- 用 Outbox 消费者发送站内通知，具备重试和死信处理。

本轮已完成前五项的核心闭环；Outbox 外发消费者仍保持关闭，避免在未配置真实通知渠道时产生外部副作用。

### P2：企业知识治理

目标：让知识库可维护、可授权、可追责。

- 知识库、文档和片段增加 `tenantId`、部门 ACL、版本、审核状态和有效期。
- 检索前执行权限过滤，禁止跨租户或跨部门引用。
- 提供文档上传、解析预览、增量索引、回滚和删除流程。
- 引用能够定位到文档版本和原文页码。
- 建立“低置信问题榜”“高频未解决问题榜”，驱动知识补全。

本轮先落地最后一项及角色授权入口。租户和文档 ACL 不能在没有租户归属数据时用默认值伪造，因此保留为需要真实数据模型参与的后续升级。

### P3：可靠性与评测

目标：用数据证明系统在边界内可靠，而不是只证明能运行。

- 建立版本化黄金数据集：问题、期望来源、期望动作、风险等级。
- 指标包含 Recall@K、MRR、答案忠实度、升级准确率、误写入率和端到端延迟。
- 在 CI 中运行不依赖真实模型的确定性回归；模型评测作为可选受控任务。
- Run Store 增加 CAS/版本控制，防止审批、取消和执行并发覆盖。
- 失败审计使用独立事务，确保业务回滚时仍保留失败证据。
- 增加结构化日志、traceId、工具耗时、模型耗时和告警。

### P4：生产化

目标：满足多实例部署、安全运营和成本治理。

- 独立 Web 前端 + BFF/HttpOnly Cookie，替换生产环境中的 Streamlit 会话方案。
- 网关统一 TLS、限流、请求大小、CORS 和安全响应头。
- 密钥进入专用 Secret Manager，支持轮换；数据库和向量库定期备份恢复演练。
- Agent、Java、Redis、MySQL、向量存储分别配置容量和故障降级策略。
- 统计每次解决、升级和模型调用成本，支持按租户配额和预算告警。

## 5. 数据与安全边界

- 浏览器只持有当前登录会话，不向聊天记录写入 JWT。
- Python Agent 校验 JWT，调用 Java 工具时同时携带用户 JWT、服务令牌和 invocation ID。
- Java 从认证上下文读取用户 ID，忽略任何模型生成的身份字段。
- 读取工具可自动执行；创建、修改、通知属于写工具，必须暂停等待批准。
- 模型无 SQL、Shell、文件系统和任意 URL 能力，工具名使用白名单。
- 当前样例知识为扫地机器人资料；接入真实企业资料前必须完成脱敏、授权和保留期设计。

## 6. 评测与业务指标

开发阶段只记录可复现的测试指标，不宣称真实业务收益：

| 维度 | 指标 | 目标方向 |
| --- | --- | --- |
| 检索 | Recall@K、MRR | 正确文档稳定进入前 K 条 |
| 回答 | 忠实度、引用覆盖率 | 结论均可由引用支撑 |
| 分流 | 升级准确率、漏升级率 | 无证据时不编造，安全问题优先升级 |
| 工具 | 审批绕过数、重复副作用数 | 必须为 0 |
| 可靠性 | 成功率、P95 延迟、恢复成功率 | 有版本基线并持续回归 |
| 产品 | 自助解决率、重复工单率 | 只有接入真实使用数据后才统计 |

`RAG_CONFIDENCE_THRESHOLD=0.58` 是当前本地样本的起始值：相关问题实测约为 0.65～0.70，明显无关问题约为 0.43～0.48。该值必须随着知识库、Embedding 模型和黄金数据集变化重新标定，不能直接当作生产结论。

## 7. 当前非目标

- 不让 Agent 自动关闭工单或自动向外部人员发送消息。
- 不用多 Agent 数量包装复杂度；只有出现明确职责和并行收益时才拆分。
- 不在没有企业数据和流量的情况下声称“节省多少人力”或“达到多少准确率”。
- 不把 Streamlit 当作最终生产前端，但保留它作为可验收的产品原型。

## 8. 下一条建议开发任务

完成 P0 验收后，优先实现“工单时间线 + 分类/SLA + 用户解决反馈”。这三项能把一次性建单升级成可追踪的服务流程，同时为后续知识缺口分析提供真实数据基础。
